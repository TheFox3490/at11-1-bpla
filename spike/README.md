# Спайк: Ursina → PNG и первый набор кадров

Цель спайка — снять главный технический риск проекта и получить реальные кадры,
на которых команда CV может начинать работу, не дожидаясь полного симулятора.

## Что проверено (и каким измерением)

| Гипотеза | Проверка | Результат |
|---|---|---|
| Ursina умеет отрендерить сцену и сохранить PNG | `00_probe_capture.py` | работает |
| Камера «вниз» даёт корректную геометрию | `01_geometry_probe.py` | пиксель↔метр, check-точки: 0,00 мм |
| Поле 6×4 м с 10 участками воспроизводимо | `02_field_capture.py` | 24 кадра + калибровочный кадр |
| Кадры согласованы с метаданными (поза) | `04_verify_frames.py` | 22/22 = 100 % видимых участков на предсказанных пикселях |
| Калибровка по 4 точкам + 2 контрольные | `04_verify_frames.py` | худшая контрольная точка 1,85 мм |
| Прогон детерминирован (seed) | повторный запуск, sha256 кадров | 24/24 кадра бит-в-бит совпали |
| Захват мыши для обзора | `07_mouse_probe.py` | в `mouse.locked` указатель прибит к центру, движение приходит только в `mouse.velocity` |
| Повторный захват без рывка | `08_mouse_relock.py` | без ручного центрирования первое движение после ПКМ давало −105°, с ним — 0,36° |

Цифры камеры: `alt = 1,2 м`, `HFOV = 70°`, `640×480` → пятно **1,68 × 1,26 м**,
**2,63 мм/пиксель**. На поле 6×4 м это требует мозаики, то есть повторных
наблюдений одной зоны — ровно того, что требует А2.

Каждый участок попадает в **2–3 кадра** из 24 — достаточно для слияния
повторных наблюдений и для проверки правила «противоречие → U».

## Запуск

```powershell
python -m venv .venv
.\.venv\Scripts\pip install -r requirements.txt

.\.venv\Scripts\python spike\02_field_capture.py    # запись прогона
.\.venv\Scripts\python spike\04_verify_frames.py    # проверка данных
.\.venv\Scripts\python spike\05_poster.py           # контактный лист + карта поля
```

Интерактивное демо (полёт камеры и дрона) — `sim/demo.py`; управление и
скриншоты описаны в корневом `README.md`.

Геометрия поля, классы участков, маркеры и текстуры живут в `sim/field.py`.
`02_field_capture.py` импортирует их оттуда же, что и демо, — правки раскладки
не нужно делать в двух местах.

Выход: `spike/out/run_spike/`

```
frames/calib.png        кадр с калибровочной доской (4 маркера + 2 контрольные точки)
frames/f001..f024.png   кадры разведки
frames/*.json           поза, время, камера, calib_id, sha256 кадра
run.json                конфиг прогона + координаты калибровочных маркеров
ground_truth.json       истинные координаты участков (только для eval/)
contact_sheet.png       все 24 кадра одной картинкой
overview_annotated.png  карта поля с классами и запретной зоной
```

## Контракт кадра (черновик, версия 0)

```json
{
  "frame_id": "f013",
  "run_id": "run_spike",
  "t_s": 18.2,
  "image": "frames/f013.png",
  "pose": { "x": 2.7, "y": 2.0, "alt": 1.24, "yaw": -0.012 },
  "camera": { "hfov_deg": 70.0, "width": 640, "height": 480,
              "mount": "nadir, fixed, no gimbal" },
  "calib_id": "calib_spike_v1",
  "sha256": "..."
}
```

`pose` — это телеметрия дрона (локальная система L, выраженная в F). Это **не**
эталонные координаты целей: истинные координаты участков лежат только в
`ground_truth.json`, и конвейер не должен его читать.

## Грабли Ursina 8 / Panda3D 1.10.16 (найдены на практике)

1. `color.rgb()` принимает **0…1**, а не 0…255. Для 0…255 есть `color.rgb32()`.
   Иначе всё, что больше 1, зажимается в 255 и сцена становится белой.
2. `Entity(texture="C:\\abs\\path.png")` не работает: Ursina ищет текстуры в
   `asset_folder` (папка скрипта). Нужно `texture=Texture(Path(...))`.
3. Одна большая текстура на квад 6×4 м отображается со сдвигом/масштабом
   (не-POT + UV). Поэтому поле собрано из **отдельных сущностей** участков —
   это и точнее, и честнее физически.
4. `base.win.getScreenshot()` в Panda3D 1.10.16 требует `PNMImage`, а не `Filename`:
   ```python
   pnm = PNMImage(); base.win.getScreenshot(pnm); pnm.write(Filename.fromOsSpecific(path))
   ```
5. `app.run()` не обязателен: цикл кадров делается через `app.step()`.
   `base.userExit()` завершает процесс — всю пост-обработку делать до него.
6. Координаты Ursina: X вправо, Y вверх, Z вперёд. Поле лежит в плоскости XZ,
   координата `y` поля = `z` Ursina. Камера вниз: `position=(x, alt, y)`,
   `rotation=(90, 0, yaw)`. При `yaw = 0`: изображение вправо = +x, вверх = +y.
7. `camera.fov` — **горизонтальный** угол. Перевод: `f_px = (W/2)/tan(fov/2)`,
   `пиксель = центр + смещение_м / alt * f_px`.
8. PNG пишется в правильном порядке каналов; `cv2.imread` читает BGR — не путать
   при сравнении цветов.
9. `mouse.locked = True` переводит окно в `M_confined`: Panda3D **сам** держит
   указатель в центре окна, поэтому `base.win.getPointer(0)` всегда возвращает
   центр, а `movePointer` ничего не меняет. Движение мыши приходит только как
   `mouse.velocity` (единицы — доля ширины окна). Если считать поворот по
   `getPointer`, камера не вращается вообще. Проверка: `07_mouse_probe.py`.

## Что осталось за рамками спайка

- Второе окно/картинка в картинке: вид от дрона + вид сверху одновременно.
- Шум, блюр, JPEG-артефакты, дисторсия объектива (сейчас рендер идеальный).
- Инъекция отказов: устаревшая поза, потеря связи, прыжок позы, просрочка карты.
- Проверка offscreen-рендера в текстуру (для кадров без окна и без мигания).
  В спайке проверен только путь «скриншот окна»; offscreen-буфер Panda3D
  работал, но его прицеливание в координатах Ursina не доверено — это отдельная
  задача на полчаса, когда понадобится картинка-в-картинке.
