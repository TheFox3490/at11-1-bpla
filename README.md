# БПЛА на агрополе — симулятор + конвейер CV

Учебный проект под задачу «Олимпиада Иннагрика 2026, полуфинал, Агротех,
задача 2» (`AT11-2.pdf`). Физического дрона нет, поэтому поле и полёт
воспроизводятся в симуляторе, а конвейер компьютерного зрения работает с
кадрами, которые симулятор записывает.

Состав проекта:

| Папка | Что это | Зачем |
|---|---|---|
| `app.py`, `sim/` | приложение с тремя режимами на Ursina | показать жюри полный сценарий: разведка → CV → миссия → исполнитель |
| `sim/demo.py` | исходная демо-сцена (свободный полёт) | регрессия: поведение и `--selftest` сохранены |
| `shared/` | общие константы, кадры, контракты, журнал | одна геометрия и один формат файлов для симулятора и CV |
| `cv/` | калибровка → детекция → объединение → миссия → маршрут → валидатор | пункты А1–А4 и Б1–Б3 задания |
| `spike/` | запись прогонов, проверка кадров, скриншоты | доказать, что геометрия камеры и разметка участков верны |

## Быстрый старт

```powershell
python -m venv .venv
.\.venv\Scripts\pip install -r requirements.txt

# приложение с тремя режимами (по умолчанию — свободный полёт)
.\.venv\Scripts\python app.py

# автопроверка всех трёх режимов без человека (разведка + CV + исполнитель)
.\.venv\Scripts\python app.py --selftest

# приёмочные испытания C1–C8 (пишут протокол в runs/tests/<id>/)
.\.venv\Scripts\python app.py --tests
.\.venv\Scripts\python app.py --tests --only C3,C6

# быстрые проверки без окна
.\.venv\Scripts\python -m pytest tests -q

# стенд в приложении: F9 → «ИСПЫТАНИЯ C1–C8», у каждого сценария своя кнопка

# скриншот конкретного режима
.\.venv\Scripts\python app.py --shot spike\out\app_free.png --mode 1
.\.venv\Scripts\python app.py --shot spike\out\app_manual.png --mode 2 --map-demo
.\.venv\Scripts\python app.py --shot spike\out\app_work.png --mode 3

# исходная демо-сцена: полетай сам

.\.venv\Scripts\python sim\demo.py --selftest
.\.venv\Scripts\python sim\demo.py --shot spike\out\demo.png
```

## Три режима

Ровно три режима, четвёртого нет. Один и тот же дрон меняет цвет и имя роли:

| Режим | Название | Что делает оператор | Цвет дрона |
|---|---|---|---|
| 1 | Свободный полёт | летает сам, ставит подсветку | оранжевый |
| 2 | Конструктор поля | рисует полигон: расставляет A/B/U, двигает, проверяет и **применяет карту к полю** | серый |
| 3 | Разведка → миссия | нажимает «1 · Разведка», ждёт CV и маршрут, задаёт бюджет/приоритеты, нажимает «2 · Исполнитель» | жёлтый → синий |

Сверху — переключатель режимов (`F1`/`F2`/`F3`) и темп `×1 / ×2 / ×5`.
Внутри кадра симуляции время идёт обычным шагом; ускорение — это несколько
подшагов по ~0.02 с, чтобы дрон не проскакивал точки съёмки и захвата кадра.

### Режим 1 — свободный полёт

Повторяет управление демо: камера-наблюдатель (WASD, ПКМ + мышь, Space/Ctrl,
Shift) и дрон (T/G — ±y, H/F — ±x, R/V — высота, P — подсветка, Backspace —
сброс). Режим не входит в зачётный сценарий и нужен для демонстрации.

### Режим 2 — конструктор поля

Это редактор **полигона**, а не карта целей. ЛКМ ставит участок или тащит
существующий, ПКМ удаляет, `1/2/3` выбирают класс A/B/U, `P−`/`P+` меняют
приоритет. Синяя рамка в левом нижнем углу — зона калибровочных маркеров:
сами маркеры скрыты (они появляются только в `frames/calib.png`), но участок
там ставить нельзя, иначе разведка не откалибруется.

Правки живут как черновик: сцена показывает их сразу, но физическое поле
меняется только после **«Применить к полю»**. Кнопки `Базовая` (вернуть
раскладку задания), `С поля` (отменить черновик) и `Очистить` помогают
быстро перебрать варианты. Применение проверяет геометрию: границы поля,
перекрытия участков, зазоры до маркеров и точки взлёта. Применённая карта
сохраняется в `data/layout.json` и переживает перезапуск; смена поля
аннулирует миссию, построенную для старой карты.

Это и есть связь режимов 2 и 3 по п. 1.2: передаётся **полигон**, а не
координаты целей. Режим 3 всё равно получает координаты только из кадров
разведки. Кнопки «Учебная миссия» и «Запустить исполнитель» оставлены как
тренировка и подписаны как ручной ввод; в зачётном сценарии их не используют.

### Режим 3 — разведка → CV → миссия → исполнитель

1. **«1 · Разведка»** — дрон-разведчик идёт по змейке: калибровочный кадр
   и 24 точки съёмки (3 полосы × 8), высота 1.2 м, скорость 0.4 м/с,
   затем возврат и посадка. Каждый кадр пишется вместе с локальной позой,
   `sha256` и временем.
2. **После посадки** автоматически запускается CV в отдельном потоке:
   калибровка по 4 маркерам и 2 контрольным точкам, детекция белых карточек,
   перспективное выпрямление, классификация по цвету и форме, объединение
   наблюдений (конфликт классов → `U`).
3. CV пишет `observation_map.json`, миссию, `mission_full.json` и `report.json`;
   миссия проходит валидатор и планировщик. **«2 · Исполнитель»** становится
   активной только если миссия валидна.
4. **Маршрут показывается до полёта**: надпись «МАРШРУТ ПОСТРОЕН», голубая
   линия, оранжевый контур расширенной запретной зоны и номера целей 1…N.
   В нижней полосе — длина, оценка времени, резерв, порядок обхода и сравнение
   двух методов (полный перебор против ближайшего соседа).
5. **Бюджет времени** `360 / 120 / 60 с` пересчитывает маршрут. Если даже
   лучший маршрут не влезает в бюджет с резервом, планировщик убирает цель с
   самым большим номером приоритета, записывает причину и делает миссию
   частичной; пропавшая цель исчезает с поля и из отчёта.
6. **Приоритеты** задаются до пересчёта: `◀`/`▶` выбирают цель, `P−`/`P+`
   двигают её в очереди, `Пересчитать` строит маршрут заново. Приоритет
   решает, **кого пропустить**, а не порядок обхода — порядок выбирает
   планировщик по кратчайшему безопасному маршруту.
7. Исполнитель читает только файл миссии, повторно проверяет контрольную
   сумму, TTL, известность калибровки и геометрию, летит по маршруту в своей
   локальной системе `L_exec`, стабилизируется 1 с в радиусе 0.25 м, открывает
   шлюз операции, включает подсветку на 2 с, возвращается и садится. Каждый
   отрезок маршрута дополнительно проверяется на пересечение расширенной
   запретной зоны, а вход дрона в реальную зону немедленно прерывает полёт.
8. **Безопасное прерывание.** Пока LED горит, шлюз перепроверяется на каждом
   шаге: истечение карты, потеря свежей локализации (> 0.3 с), потеря связи,
   выход из радиуса или коридора высот гасят индикатор. Дальше миссия
   завершается штатно: возврат на базу и посадка либо аварийная посадка на
   месте, если навигация ненадёжна. Это не «ошибка», а статус `aborted` с
   причиной в журнале и отчёте; в режиме 3 появляется строка «МИССИЯ
   ПРЕРВАНА».
9. **Стенд испытаний C1–C8** открывается по `F9` и не является четвёртым
   режимом: это сервисный оверлей над теми же тремя режимами. Слева список
   сценариев с кнопкой запуска и статусом PASS/FAIL, в центре — живое поле с
   маршрутом, точками включения LED и точкой прерывания, справа — карточка
   «ожидалось / получено / задержка / доказательства» и 2D-карта поля.

Реестр действий `state/action_registry.json` долговечный: повторный запуск
той же миссии не выполняет операции заново (все цели блокируются как
`duplicate_action_blocked`). «Сброс сценария» очищает состояние режима, но
не стирает реестр.

### Что общего у режимов

- Один дрон, одна камера, одна сцена; роль меняется только цветом и именем.
- Панель отчёта — часть режимов 2/3, отдельного режима отчёта нет.
- Все координаты на экране — в поле F; внутри дрона — в его локальном кадре.

| `sim/modes/*` | интерфейс и сценарии трёх режимов |

клон стартует с раскладки задания. `sim/demo.py` и `spike/` по-прежнему
рисуют жёсткую раскладку из `sim/field.py` — это осознанная регрессия,
редактор поля живёт только в приложении.

## Конвейер CV и файловые контракты

CV **не импортирует** `sim/field.py` и **не читает** `ground_truth.json`.
Единственный вход — каталог прогона разведки:

```
runs/<run_id>/
  frames/calib.png|json          калибровочный кадр и поза
  frames/f001.png|json ...       кадры съёмки, локальная поза, sha256
  run.json                       маркеры, чек-точки, параметры камеры
  calibration.json               оценка L -> F и ошибки
  detections.json                все детекции по кадрам
  observation_map.json           объединённые объекты
  mission_candidate.json         миссия до валидации (с учётом бюджета)
  mission_full.json              полная миссия CV без усечения по бюджету
  plan.json                      маршрут, сравнение методов, пропуски и бюджет
  report.json                    итоговый отчёт для панели
missions/<mission_id>.json       валидная миссия (граница для исполнителя)
data/layout.json                 применённый полигон поля (режим 2)
state/action_registry.json       подтверждённые действия
runs/tests/<bench_id>/           протокол C1–C8, 2D-карты, таймлайны, снимки
```

Миссия — обычный JSON в поле F; контрольная сумма считается по всем полям,
кроме самого `checksum`:

```json
{
  "mission_id": "mission_...",
  "coordinate_frame": "F",
  "units": "m",
  "created_at": "...Z",
  "valid_until": "...Z",
  "calibration_version": "calib_...",
  "targets": [
    {"target_id": "T01", "action_id": "...-T01", "klass": "A",
     "point": {"x": 2.096, "y": 0.703}, "position_error_m": 0.07,
     "priority": 1}
  ],
  "forbidden": [{"zone_id": "NFZ-1", "vertices": [...]}],
  "rejected": [...],
  "budget_s": 60.0,
  "partial": true,
  "skipped": [
    {"target_id": "T06", "priority": 6, "point": {"x": 2.592, "y": 3.191},
     "reason": "insufficient_time_with_reserve", "budget_s": 60.0}
  ],
  "checksum": "..."
}
```

Валидатор пересчитывает контрольную сумму, проверяет TTL (`valid_until`
не позже последнего кадра + 15 минут), уникальность id, класс A, границы
поля, простоту и площадь полигонов, запас точности и расширенную запретную
зону. Бюджет точности: 0.07 м на разведку (предел 0.13 м) + 0.06 м
исполнитель + 0.02 м выставление + 0.04 м радиус воздействия < 0.25 м.

## Точность и проверки

Калибровка оценивает преобразование L → F по четырём маркерам; контрольные
точки в кадре дают остаточную ошибку порядка 0.1 мм. На полном прогоне
10 объектов легли на эталон с ошибкой 5–22 мм — заметно ниже лимита 70 мм
на входе миссии.

## Демо-сцена `sim/demo.py`

Исходная сцена сохранена без изменений по поведению и используется как
регрессия. Камера наблюдателя и дрон — **разные объекты**.

### Камера наблюдателя

| Клавиша | Действие |
|---|---|
| `W` `A` `S` `D` | вперёд / влево / назад / вправо (по направлению взгляда) |
| `ПКМ` (зажать) + мышь | вращение камерой; отпустил ПКМ — мышь снова обычный курсор |
| `Space` / `Left Ctrl` | вверх / вниз |
| `Left Shift` | ускорение ×2,5 |

Мышь не захватывается постоянно: указатель прячется и центрируется только
пока зажата правая кнопка. Это специально — иначе на ноутбуке нельзя
переключиться в другое окно.

Чувствительность — около 0,18° на пиксель при окне 1280×720
(`MOUSE_SENSITIVITY = 130` в `sim/demo.py`, «градусов на ширину окна»).

### Дрон

| Клавиша | Действие |
|---|---|
| `T` | вперёд (+y поля) |
| `G` | назад (−y поля) |
| `F` | влево (−x поля) |
| `H` | вправо (+x поля) |
| `R` / `V` | выше / ниже (коридор 1,0–1,4 м) |
| `Left Shift` | ускорение ×2,5 |

Дрон сам разворачивается носом по направлению движения. Команды заданы в
осях поля, а не в осях дрона: так детям проще — «T всегда вперёд по полю».

### Прочее

| Клавиша | Действие |
|---|---|
| `C` | переключить вид: наблюдатель ↔ камера дрона (вниз, 70°) |
| `P` | подсветка полезной нагрузки (индикатор «операции» из задания) |
| `Backspace` | вернуть дрон в точку старта |

В виде от дрона окно 16:9, а настоящий кадр — 4:3. Поэтому по бокам
появляются чёрные поля, а угол объектива пересчитывается так, чтобы видимая
часть была ровно кадром 640×480 с `HFOV = 70°`. Служебные оверлеи (сетка,
запретная зона, отвес, след) в этом режиме скрываются — видно только то, что
увидит CV.

### Что видно на экране

- **Поле 6×4 м**, сетка 1 м, красная ось — `x`, зелёная — `y`, начало
  координат в углу поля.
- **10 участков**: 8 класса A (из них 2 внутри запретной зоны), 1 класса B,
  1 неопределённый `U`. Класс кодируется и цветом, и формой — так его можно
  распознавать даже в ч/б.
- **Красная запретная зона** — полигон, внутрь которого дрону нельзя.
- **Дрон оранжевый**, с винтами, светодиодом и **отвесной линией до земли**:
  по ней сразу видно, над каким участком он висит.
- **Жёлтый след** — траектория. Он же пригодится, когда появится
  автоматический маршрут.
- **HUD**: координаты, высота, скорость, курс, режим камеры, состояние
  подсветки.

Модель дрона нарисована в **1,6× реального размера** (`DRONE_SCALE` в
`sim/demo.py`): настоящие 30 см с высоты 5 м выглядят как точка. На расчёты
координат это не влияет — масштаб только у меша.

## Модель камеры (одна на симулятор и конвейер)

| Параметр | Значение |
|---|---|
| Угол обзора | `HFOV = 70°` (горизонтальный) |
| Кадр | 640 × 480 |
| Высота | 1,0–1,4 м, номинал 1,2 м |
| Пятно на земле | 1,68 × 1,26 м |
| Разрешение | 2,63 мм/пиксель |
| Ориентация | надир, без подвеса |

Поле 6×4 м целиком в один кадр не влезает — нужна мозаика из повторных
наблюдений. Это и есть суть пункта А2 задания.

## Общая геометрия поля

`sim/field.py` — раскладка задания по умолчанию: координаты участков, классы,
запретная зона, параметры камеры, генерация текстур. Демо и запись кадров
импортируют его напрямую; приложение берёт раскладку из `sim/scenario.py`
(по умолчанию — та же, но её можно изменить в режиме 2 и применить). Поэтому
сцена и данные не могут разъехаться.

```
F: начало координат в углу поля
   x — вдоль стороны 6 м
   y — вдоль стороны 4 м
   метры; Ursina: (x, высота, y)
```

`validate_layout()` при старте проверяет инвариант задания: 10 участков,
8 классов A, из них 6 доступны и 2 внутри запретной зоны, участки не
пересекаются.
